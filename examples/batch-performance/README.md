# 批量笔记调查的并发与恢复实测

在项目根目录执行以下命令。需要 JDK 17+、Python 3.9+ 和 macOS 或 Linux。首次构建使用 Maven Wrapper 下载依赖。测试在本机回环地址使用临时端口和临时 H2 数据库。

```sh
./backend/mvnw -f backend/pom.xml package
mkdir -p work
python3 examples/batch-performance/replay.py --pairs 3 --output work/batch-performance.json
```

## 本机结果

在 macOS 26.4 arm64、10 个逻辑 CPU、Corretto 17.0.21.1、Python 3.9.6 上，25 篇笔记的完成时间中位数从 1.601 秒降至 0.507 秒，约为 3.15 倍加速。三组有序结果逐项相同。记录时间、精确数值和文件摘要见同目录的 `results.json`。

| 配对 | 单路（秒） | 四路（秒） | 单路 / 四路 |
|---|---:|---:|---:|
| 1 | 1.600502 | 0.507301 | 3.15 |
| 2 | 1.584060 | 0.505454 | 3.13 |
| 3 | 1.614057 | 0.545151 | 2.96 |

强制终止发生在 4 篇结果已提交时。重新打开数据库仍可读到这 4 篇，恢复阶段只启动了其余 21 篇的分析。完成后的 25 条结果与单路运行逐项一致。

## 计时口径

将 `examples/batch-upgrade` 的 5 篇笔记各生成 5 份，文件名和记录编号不同，共 25 篇。预期为 10 篇修改、5 篇保留、5 篇追问、5 篇无关。这组重复样本用于比较执行耗时，独立内容只有 5 类。

脚本通过 HTTP 导入笔记和两份版本资料，等待索引发布，然后在同一数据库、同一数据代次上交替测试 1 路和 4 路。每个配置启动新的 JVM，先完整预热一批，再计时一批。墙钟从发起创建批次的 POST 开始，到客户端第一次收到完成的 GET 为止。服务器和客户端均以 25 毫秒间隔轮询。计时涵盖 JVM 调度、原件校验、Python 子进程、SQL 提交与 HTTP，并排除 JVM 启动、导入、建索引与预热。每次调查调用真实 Python CLI，计时阶段没有额外延时或调用记录包装器。

每批逐项检查全部 25 个完整 JSON 对象，包括顺序、编号、原稿、补丁、问题、理由、证据、轨迹与接受状态。原始时长、运行次序、逐篇内容摘要、两份资料摘要及机器信息均保存在 `results.json`。本项测量覆盖本机 H2 和 Python 子进程路径；远端分析 HTTP 部署、MySQL、多用户吞吐和大规模资料库需要分别测量。

## 中断与恢复

恢复实验另建一个批次。首次看到部分结果时，向自建的 Java 进程发送 SIGKILL。在同一个数据库上启动暂缓批处理的 JVM，再次读取已提交结果，记录精确的持久化边界。随后按原批次编号重启处理，检查每一条已提交结果的内容和最终有序列表。只有恢复实验记录 Python 分析器的实际启动文件名，用于验证恢复后的调用集合恰好等于尚未提交的文件集合。意外终止时已经开始、尚未提交的只读调查可以在恢复后重新执行。

生产默认 `review.batch.parallelism=4`，允许 1 到 16。协调线程按完成顺序写入结果，数据库按原编号返回。每项写入核验租约令牌并延长租期，已写入的结果受 `result_doc IS NULL` 条件保护。默认 `review.batch.lease-ms=120000`，恢复实验设为 4000 毫秒以缩短等待。
