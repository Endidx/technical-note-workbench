# 一次审阅会读到哪些数据

`scripts/evaluate.py` 的 `load_cases` 会读取指定 gold 清单和清单列出的所有 Markdown，检查标签和引用，再逐案调用 `evaluate_case`。清单决定测哪些笔记，标签和引用决定怎样计分。完整结果 JSON 含 gold 和原文。单案调用的输入如下。

| 入口 | 单次调用使用的数据 |
| --- | --- |
| fixed | `analyzer/engine.py` 的 `analyze_note(path)` 重新读取这一个文件，以代码和正文判断；输出带文件名和从文件名生成的 ID。 |
| direct | 固定系统指令、当前 Markdown 全文、`examples/sources` 下两个指定版本的资料快照和固定输出约束。 |
| agent / agent-model | Harness 接收文件名、该案原文、修订 0 和意图模式。每案单独初始化状态。加载共用的两份迁移资料，并提供 1.0.2 版本参照快照；评测报告另存参照目录摘要。评估首次调用没有用户回答、配置补充或旧检查点。 |

意图判断从当前 Markdown 中选取有效正文、拆分证据句；代码内设有固定指令及示范问答，某些复核阶段还会传入本案前一步的候选判断。语义请求不附 gold、案例 ID 或其他待测笔记。文件名和修订会进入检查点来源摘要和代码检查的调查记录。`remote` 工具规划器接收已完成的调查记录，因而可能看到文件名和修订。如果文件名暗示答案，使用远程规划器时需要把它当作可见输入。离线规划按允许的工具顺序执行。

工作台的 `HarnessService.investigate` 按用户选择的笔记和修订读取数据库里的 `current`，续问或恢复时可增加回答、配置事实或检查点。本地 `run.sh` 从 `examples/notes` 生成初始固定流程结果；资料库搜索有独立的 `/api/library` 入口。上述单案迁移调查没有调用资料库检索。改变评估期的标签会改变计分；过去用案例开发过的规则、词表及提示示范仍会影响今后的判断。仅凭运行时输入检查无法证明训练数据独立或新笔记上的准确率。

从项目根目录运行 `python3 -m unittest scripts.test_evaluation_boundary -v`。测试固定原文，替换 ID、标签、标注理由、标注引用和文件名，比较 direct 请求与 offline 规划下 agent-model 首次语义请求，并核对模拟模型回复后的第一个用户可见决定。测试使用模拟 HTTP 传输，无需模型服务。
